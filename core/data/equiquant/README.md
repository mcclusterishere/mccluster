# MOSAiC replay input

`observations.json` is the unmodified derived table from the [MOSAiC scaling pilot at commit 523112d](https://github.com/mcclusterishere/mccluster/tree/523112ddbcd2b9dfcc16891437f83a5781d045fb/tools/research/mosaic-scaling). The table contains 13 sampled weekly acquisition pairs, four sensitivity configurations and three projected target scales (2.8, 5.6 and 11.2 km).

Observations derived from Luisa von Albedyll and Nils Hutter (2023), *High-resolution sea ice drift and deformation from sequential SAR images in the Transpolar Drift during MOSAiC 2019/2020*. The pilot aggregated the signed gradient fields into regional rates. The derived table retains [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). [Dataset DOI](https://doi.org/10.1594/PANGAEA.958449)

Core refits the selected model using the committed observations. It hashes the compact, recursively key-sorted UTF-8 result JSON with SHA-256 after rounding numerical outputs to ten decimal places. Each reference hash comes from the same projection of the pilot's [validation.json](https://github.com/mcclusterishere/mccluster/blob/523112ddbcd2b9dfcc16891437f83a5781d045fb/tools/research/mosaic-scaling/results/validation.json), whose original byte hash is `d8bf3774c046fda94ddc8775996b6ebf5397c2385d50aadceeaa155232285d7e`. A match covers the training counts, classifications, thresholds, errors and summary scores for every held-out week.

## Execution targets

A target-enabled Core runner uses the canonical queue and its existing service credential. An operator sets `MCCLUSTER_EQUIQUANT_TARGET` to `prime` for a local research-only runner or `ovh_core` for the deployed Core service, and supplies that installation's `MCCLUSTER_EQUIQUANT_MACHINE_SHA256` privately. An operator on the intended machine obtains that value with `node --input-type=module -e "import {mosaicMachineSha256} from './core/src/equiquant-runtime.mjs'; console.log(mosaicMachineSha256())"` at the repository root. It binds the OS installation identity, hostname, architecture and CPU inventory. OVH also requires the canonical deployment path and manifest. Existing installations advertise no capability until configured. A local research-only runner does not claim other Core jobs.

Before eligibility, the runner hashes the input and kernel, runs all three models, checks every reference result and the actual fold coefficients, and signs its tested capability with an in-memory Ed25519 key. Registration through the existing service-authenticated database channel binds the key to the worker. It refreshes at 30 seconds and expires after 120. An ordinary workspace caller cannot register a worker. Restarted workers must pass the probe again. A queued run remains tied to the same target, hardware and Node runtime. The key bound at claim verifies that run's receipt. Existing connected inference adapters do not implement this CPU kernel or attest its arithmetic precision.

The signed spec includes the dataset DOI, upstream commit, input and executable-kernel digests, fitted model digests, precision and timing scope. A model digest covers the threshold, intercept and slope actually used for each held-out prediction across all four configurations. Each signed run receipt also binds the workspace, project, job, selected model, hardware, observed Node version and deterministic result. Runtime uses a monotonic clock around the complete binary64 refit, excluding queue wait, input loading, hashing and signing. Timings from different target, hardware, backend, runtime, precision or spec stay separate.
