# Reviewed releases and in-mission learning

This continuation joins the existing news metadata store, #762's generated-mission compiler, #768's real database acceptance and #774's verified practice continuity. It does not change those active branches or #781's City engine. Serial integration must include those dependencies before this change. Production activation is not part of this implementation.

## Player and reviewer journey

`prim3-released-mission.html` uses the existing house-owner gate. The owner chooses an existing recent news article or labeled offline practice, reviews the public source and regional geography, selects one of the existing restore/survey/recover templates and approves an immutable release. No freeform news narrative or named adversary enters generated mission instructions. Publisher review is an owner's explicit attestation, not an assertion that an automated system established a story's truth. News discovery reuses `media_news_articles`; no collector, paid model, operational Halo feed or competing news pipeline is added.

The saved release supplies its immutable recipe to the existing generated tactical level. The mission runs in a same-origin frame beside checkpoint math. The canonical local resolver still controls movement, AP, threats, objective actions and extraction. The shared `released-learning.mjs` adapter waits for the corresponding local objective step before presenting its question. The API independently validates the registered checkpoint, current server-issued question and answer; it signs durable evidence. Local checkpoint state is presentation context, not server-proven tactical completion. The debrief labels tactical outcome as the player's report and awards no Principles credit, rating or credential.

The server registers every generated objective step (for example `CHECKPOINT-1:STEP_2`). Each correct answer advances the math checkpoint; wrong answers generate another problem at that checkpoint. Hints preserve their scaffolding status. A completed debrief requires all math checkpoints; an abandoned debrief remains available after an attempt, including at the bounded event limit. The reviewed recipe identity and digest bind each learning session. Another tab/variant can reuse the adapter with its registered release and canonical local state; metric/hex learning still needs a separately specified evaluator and is not inferred from opaque graph indices.

## Time, durability and authority

- News expires at **publication + 24 hours**. Review cannot extend old news. Offline releases expire at **database review time + 24 hours**. Reload, retry and re-review do not change either timestamp.
- The pending schema stores immutable recipe inputs, a SHA-256 compiler-output digest, source metadata snapshot, owner/reviewer identity, registered checkpoint IDs and expiry. First revocation is the only ordinary update. Source URL/date/country are rechecked against the existing article inside publication, preventing a stale metadata read from being committed as the current source.
- Publication serializes by owner/deduplication key. Exact retries return the original receipt. A conflicting revision is rejected rather than overwriting it. News deduplication is per article/objective; offline deduplication uses normalized input excluding review identity.
- Claiming a release and creating its learning session/binding is transactional. Concurrent identical claims return one session; conflicting identities fail. Session ownership is supplied by the existing house-owner authentication callback, never a request body.
- New event inserts lock and check the release inside PostgreSQL. Expiry/revocation therefore cannot be bypassed with a stale browser clock or an earlier API read. Accepted historical receipts and debriefs can be read/retried after expiry; no new answers are accepted. The existing append-only chain still owns sequence and rollback.
- The new tables have RLS enabled with no anon/authenticated access. Only the existing gated Worker uses the service-role API. RPCs are invoker functions restricted to service_role. The trigger's narrow definer function reads private release bindings and is not client-callable.
- Account erasure uses the existing `learning.allow_purge` transaction convention, with cascading dependent bindings. No erasure or production schema change was performed here.

It covers source-derived publication, exact retry, duplicate/conflict protection, concurrent claims, checkpoint binding, wrong checkpoint rejection, server expiry, revocation, preserved receipts, private table/RPC access and no competency writes.
