# OVH deployment drain boundary

The canonical deployer drains the durable Core runner and local compute node before replacing their code, adapter, broker or Ollama configuration. This is native systemd deployment, not a second queue or execution service. All accepted jobs and compute leases stay in the existing Supabase tables.

## Sequence

1. Validate the exact checkout, acquire the installation's deploy lock and run Core checks/tests. Optional missing-model downloads share a two-minute budget while the old release is still serving work, before the maintenance window.
2. For the existing runner, install an exclusive temporary runtime `Restart=no` override, reload systemd, and signal only its main PID with SIGTERM. Its existing handler stops claiming and completes its current job, including heartbeats and durable completion. Do not use `systemctl stop` here: its stop timeout can force-kill work and its default control-group signal can kill job subprocesses.
3. Once the runner exits, use the existing Core environment and the local node's public identity to set only that canonical node from `online` to `draining`. The deployed lease-v2 database contract serializes this with claims on the node row. New claims stop; existing leases can still start, heartbeat and complete. Save a non-secret recovery receipt before the state write, including before an ambiguous/lost response.
4. Wait until that node has no `leased` or `running` leases, including expired-but-unfinished records. Only then stop its process. Never equate adapter `busy=false` or lease expiry alone with a safe drain.
5. Snapshot and replace the release. Restart dependencies first and check the adapter. Start the compute node, restore its original canonical state, remove only the deployer's runner override, and start the runner. Run the normal complete health gate. Rollback drains again before replacing dependencies, then uses the same startup order.

## Failure behavior

- The default shared runner-plus-compute drain budget is 660 seconds. A timeout before live file changes returns a failed/deferred deployment, keeps dependencies untouched, restores the canonical node state and runner restart policy, and requests the previous services to start. If the runner is still finishing, it is not killed: `Restart=always` takes effect after it exits naturally. This may delay service recovery; it is not a claim of immediate availability.
- ERR, TERM, INT and HUP trigger recovery. During recovery Bash and the bounded Node end-drain helper ignore additional catchable termination signals; Node needs its own handler because it resets inherited signal defaults. A foreign/stale runtime override or an already-transitioning producer defers deployment. Manual and reconciler deploys use one host lock.
- Preexisting operator `draining` state stays draining. Recovery never clears quarantine or revocation. Do not concurrently change the same node's drain state manually: the existing schema has no drain-owner token, so a second indistinguishable manual `draining` update cannot be attributed separately.
- A recovery API failure keeps the receipt and reports an error, rather than claiming recovery. Re-running the helper's `end` action with that receipt rereads canonical state, so a lost response after a successful resume does not require a second write.
- If restored dependencies are unhealthy or files cannot be restored, consumers remain paused instead of taking jobs against broken dependencies. This is a loud recovery failure requiring operator attention, not a successful rollback.
- SIGKILL, power loss, disk failure, or repeated interruption during recovery cannot be repaired by shell traps. Inspect the backup's `compute-drain.json` and the exclusive runtime override before manual recovery. Never remove an unknown operator-owned override or blindly set a node online.

## First rollout and production checks

The protocol works with the existing runner signal handler and lease-v2 compute node, without requiring a new handler in a running process. Before promotion, verify the live database has the lease-v2 row-lock/state behavior, the canonical house/node identity matches, Node supports `--env-file`, and the actual systemd unit honors the runtime `Restart=no` override. The helper uses existing `/etc/mccluster/core.env`; it adds no credential, permission or grant. Missing access fails closed.

The tests exercise the actual shell drain/rollback functions with fake systemd and API transports. A real Linux process-group test signals a Bash wrapper, deployer and Node helper together, then signals their recovery again. It proves catchable-signal cleanup behavior, not live systemd cgroup timing or live Supabase state. This workspace does not run systemd as PID 1; live unit behavior still needs a staging check.

This is not a zero-downtime release. Queue consumption pauses while dependencies restart. Accepted durable jobs remain queued. Broker HTTP requests, manually invoked loopback `/execute` or `/embed` requests, custom clients and OpenCode traffic are not covered by the durable-consumer fence. The current broker's resident-turn and compute tools enqueue durable work, but an in-flight HTTP response can still be interrupted by its restart. If arbitrary callers require uninterrupted service, obtain a short maintenance window or first add and validate ingress draining; do not claim this patch drains them.

The reconciler keeps its 20-minute start limit and gains a separate, bounded 20-minute stop/recovery allowance with explicit `KillMode=control-group`. This is required because systemd signals the wrapper, deployer and helper together on a start timeout, then escalates after the stop allowance. Recovery may need a second 660-second drain, plus bounded API requests, dependency restarts and health checks. No privilege or cgroup containment setting is relaxed. Normal budgets are two minutes of optional downloads, up to 11 minutes of drain, and the existing check/start/health budget. Pathological disk or systemd failures and SIGKILL are still outside a shell trap's guarantees.

## Two-pass first rollout

The currently running reconciler began under its old unit. Before any drain or optional model pull, the deployer matches systemd's inherited invocation ID and checks the running unit's effective stop grace, kill mode, start-timeout failure mode and lifecycle state. The incoming service file never substitutes for this check.

If the guard fails, a tightly scoped bootstrap is eligible only for the known legacy combination: matching invocation, active/activating lifecycle, a 20-minute start limit, a 90-second stop grace, `KillMode=control-group`, and terminate-on-start-timeout. Unknown settings or a stopping unit remain fail-closed.

The first pass may atomically install only `/etc/systemd/system/mccluster-vps-reconcile.service.d/90-mccluster-recovery-timeout-bootstrap.conf`, containing an ownership comment and `[Service]` / `TimeoutStopSec=20min`. It does not change KillMode, grants, credentials, network settings, restart policy or any workload. It refuses symlinks, unsafe ownership/modes, foreign contents, and any other explicit `TimeoutStopSec` or `TimeoutSec` assignment. Because `systemctl cat` can omit not-yet-loaded drop-ins, a bounded unit-path lookup also checks on-disk generic, dash-prefix and exact-name drop-in directories before installation. Installation uses a no-replace hardlink from a complete staging file; its inode identifies what this invocation may undo.

Manager operations in this bootstrap are bounded to five seconds with one additional second before forced CLI termination. After daemon-reload, the effective invocation, lifecycle, start limit and unchanged kill/failure modes are checked again along with the desired stop grace. **Even when those checks pass, the deployer exits 75 without pulling models, draining producers, replacing code, restarting workloads or stamping the release.** The existing two-minute timer supplies the next invocation, which must independently pass the ordinary, unchanged effective-state guard. No assumption is made that reload retroactively changed an already armed deadline. The first pass will appear as a temporary failed/deferred reconciliation, not a successful code deployment.

The owned drop-in intentionally persists across later code or unit rollback and reboot. Recovery grace must not disappear just because an older unit file is restored. It is not removed by normal release rollback. An interrupted prior install with the exact owned contents can be reloaded idempotently, but that invocation still exits before deployment. A failed new bootstrap removes only the file proven to share its staging inode, reloads, and verifies the prior effective grace. A foreign or concurrently replaced file is never deleted. If manager recovery cannot be verified, report the recovery failure rather than claiming configuration restoration; workloads remain untouched.

The real process-group test covers termination of the wrapper, bootstrap and bounded reload CLI, and verifies timeout-only rollback without workload actions. A hung kernel/filesystem, SIGKILL/power loss or an unresponsive manager can still prevent verified cleanup. On unsupported or conflicting configurations the guard-only/manual-supervisor path remains available: an authorized timeout-only installation/reload must be verified before another attempt. Never restart the active reconcile job merely to alter a deadline.

Upstream semantics: [systemd service timeouts](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml) define start-time termination followed by the stop grace; [systemd kill modes](https://github.com/systemd/systemd/blob/v257/man/systemd.kill.xml) describe whole-cgroup termination and eventual forced kill.

A metadata-only manifest refresh is intentionally not implemented: the broker's deployment SHA is startup-bound. Editing its manifest while leaving the old process running would not attest the new release truthfully.
