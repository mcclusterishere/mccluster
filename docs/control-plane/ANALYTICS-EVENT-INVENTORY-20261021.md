# Analytics Step 4: event dictionary and external source truth

- The raw `events` and derived `events_lean` tables remain the canonical first-party evidence. The new **owner-only on-demand** endpoint `/v1/analytics/event-inventory` reads every distinct first-party event name from both stores through a gated service-role RPC. It reports raw and lean totals separately, bot row count, preceding 24h/7d volumes, first/last observation, current taxonomy stage, and missing classification or projection mismatch. It never equates page views with people or sums incompatible units.
- A curated set of **30 low-risk event-name classifications** is added to `event_taxonomy` with explicit notes. This does not reclassify existing mapped names; `ON CONFLICT DO NOTHING` protects prior review. The versioned measurement dictionary `analytics-dictionary/2026-10-21.1` contains exactly the same 30 event names, stages and notes, plus source references, and an exact-match test keeps both representations in sync. A client `signup_started` signal is **engage**, not account registration; `signup_succeeded` remains explicitly unclassified until provenance is reviewed. `form_submit` is a client-reported lead, not a verified backend submission. `music_full_play` is listening telemetry, not payment. `mission_join` is not proof of an assignment.
- The first-party `Control > Analytics > Data explorer > Events` view lists name-level counts, classification, data parity, filter and unknown coverage. It also shows Instagram source status from actual scoped `social_accounts` and a dedicated service-only SQL RPC that counts only `social_posts` whose account has `platform='instagram'` and `social_metric_snapshots` with source `platform_api` for those Instagram posts. Manually reported snapshots and other platforms never prove Instagram observations. No token, handle or credential data is returned.
- Current observed Instagram connectivity includes one row flagged `meta_error_190` and no discovered media or metric snapshots. Reconnection requires interactive consent; **the code cannot authenticate on the owner's behalf** without that OAuth flow. Until approved reconnection, the UI reports authorization-required/unmeasured, not fabricated 0 reach.
- Backends and schema retain existing RLS; the new SQL function uses `SECURITY INVOKER`, revokes PUBLIC/anon/authenticated execution and grants service_role only. The worker route invokes `requireHouseOwner` before any queries. No third-party metrics are synthesized.
- The full event-name review manifest records 78 observed unmapped names, not just the 30 curated entries. Remaining unmapped or ambiguous names stay visible with `unclassified` status; they are not silently mapped to `engage`, registration, purchase or conversion.
- SQL migration must be applied and the canonical ledger reconciled **before** the Worker/API is deployed; do not deploy from a PR whose RPC has not been applied. Acceptance: isolated PostgreSQL and Worker tests, owner/staff rejection, independent raw/lean comparison, all-time and 24h/7d checks, explicit unknown names, and provider OAuth reconnection only after authorized user interaction.

## Reliability preflight

The all-history event inventory originally scanned large first-party `events` and `events_lean` heap tables and a read-only query plan took more than eleven seconds, above the dashboard's eight-second PostgREST cancellation threshold. Before applying the migration to a **populated** live collector, build both narrow first-party partial covering indexes in **separate non-transactional `CREATE INDEX CONCURRENTLY` statements** from `supabase/ops/analytics-inventory-index-events.sql` and `supabase/ops/analytics-inventory-index-lean.sql`. Verify both indexes are valid and ready in `pg_index`. The migration has an explicit populated-table precondition that **refuses to proceed** if either valid prebuilt index is absent; this prevents ordinary `CREATE INDEX` from blocking live inserts. On an empty test/replay database the migration itself can create the indexes. A five-second lock timeout guards short index metadata checks; it does NOT limit how long ordinary index creation could block writers. This reduces heap I/O but does not guarantee specific latency under all workloads: verify the exact RPC with `EXPLAIN (ANALYZE, BUFFERS)` and the actual owner-authorized API after deployment. Keep migration promotion blocked until the query meets the existing timeout without relaxing permissions or changing the global statement timeout.

One owner-scoped service-only SQL RPC returns the COMPLETE Instagram account count, connected count, provider-API post count, provider-API snapshot count and Meta error-190 presence. No API-side `LIMIT 100` or unordered account scan can silently truncate this read. A failed RPC makes **all counts null/unavailable** and sets `partial=true`; known authorization expiry cannot override a missing provider read. A source showing zero imported provider-API measurements remains distinct from a missing source read. Manual reports and other platform rows are excluded from provider verification.

The production prebuild and the subsequent migration are two controlled operations. A concurrent index is not recorded as a complete Analytics migration by itself; do not deploy the owner API until the canonical migration ledger is updated, the function privileges are verified, and a fresh production EXPLAIN shows acceptable performance under the existing timeout. Never apply these prebuild scripts inside a transaction.
