## Owner first, then scoped delegation

Proposed effective permission is the intersection of authenticated identity, enabled membership, granted capability, resource/tenant ownership, release/entitlement eligibility and any required approval. Evaluate it server-side for every read and write; repeat critical ownership constraints in database policies/transactions. Navigation is only a presentation of that decision.

| Actor | Intended control | Must remain outside that grant |
| --- | --- | --- |
| Installation/house owner | Supported installation settings, product releases, grants, billing policy and recovery | Secret plaintext in ordinary forms; arbitrary code execution through settings; bypass of immutable ownership or transaction integrity |
| Delegated admin | Named capabilities in named workspaces/resources; optional expiry | Self-escalation, changing house ownership, cross-tenant reads, automatic access to private Halo/LMS or infrastructure |
| Creator | Own projects, catalog, media, storefront and approved publishing | Other creators' drafts/assets, grant issuance, provider-verified settlement fields |
| Member | Own profile, participation and licensed product state | Moderation/self-verification, administrative configuration or another person's saves |

The owner grants a named capability and scope, sees the resulting permissions, confirms, and can revoke it with an audit receipt. Prevent removing the last owner. Role preview uses synthetic/redacted fixtures and the real policy evaluator; it must not issue another user's token or let an owner accidentally publish as them. A preview never changes actual permissions. In-flight privileged jobs must recheck authority before consequential execution after revocation.

1. **P0: Establish truthful readiness and recovery.** Add a read-only capability inventory to existing System navigation, backed by actual schema/provider/config checks and last-known-good timestamps. Inventory route, owner workflow, authoritative store, allowed roles, release state, current blocker, recovery action and tests. Preserve existing IDs. Done when every advertised owner button either completes its workflow or names an actionable blocker without fabricated success.
2. **P1: Finish one owner settings loop.** Extend the current front-page editor with server-validated settings, private draft, preview, revision diff, optimistic version check, explicit publish, audit receipt and restore-as-new-revision. Reuse site history and reconciled Studio contracts. Add admin layout/favorites over registered route IDs, with a permanent reachable recovery route. Done when Matthew can edit, inspect, publish, reload and restore on phone/desktop with AI disabled and no shell.
3. **P1: Finish owner product management.** Register independent Globe products (News, Travel, Missions, Finance, Games and applicable Music experiences) with dependencies, settings schema, data/source rights, capabilities, jobs and readiness. Separate visibility from authorization. Disabling a product refuses new server operations and drains/cancels work according to its contract; records and purchased access histories survive. Finance architecture remains with its specialist workstream.
4. **P2: Close the complete owner journeys.** LMS authoring/versioned course imports; Studio/media preparation and recovery; music release; commerce payment-to-entitlement-to-refund; social publish/retry; operations diagnostics and recovery. Integrate narrow reviewed portions of #681 on current main instead of launching its whole stack at once. Each journey must demonstrate failure and recovery, not only its happy path.
5. **P2: Delegate the same capabilities.** Add explicit scoped grants, per-role forms, server checks, entitlements, audit and safe previews. Prove with two unrelated tenants and multiple creators. Do not automatically promote owner-only private tools to lower roles. The current LMS/Halo privacy restrictions remain until separately changed.
6. **P3: Package independent editions.** Keep this separate from hosted tenancy and from operating Matthew's installation. The existing `docs/products/DISTRIBUTABLE-PRODUCT.md` is the release contract. The local audit reports **143** runtime/config files with known production bindings and **203** SQL files requiring classification. These are portability findings, not 143 leaked secrets or 203 defective migrations. Build a neutral configuration profile, reviewed distribution allowlist, clean schema baseline, fresh-owner bootstrap, dependency notices, upgrades and tested restore. Never ship production Git history, personal media, transcripts or seeded customers.

Proposed settings lifecycle: validate → save private revision → preview under selected role → compare impact → authorize publish → atomically activate version → audit → monitor → restore a prior compatible version as a new revision. Revision writes require expected-version matching and request idempotency. Rollback does not reverse a charge, sent message or incompatible schema migration; those require compensating actions and specific runbooks.

Routine content, layout, module settings, approved integrations and bounded job recovery belong in Control. New executable adapters, schema evolution, deployment topology, credential rotation, provider purchasing and disaster restore remain elevated workflows. Control can eventually initiate reviewed runbooks and display their receipts, but a generic settings editor must not become a terminal.
